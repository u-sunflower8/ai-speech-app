# AI話し方診断アプリ 要件定義書

## 1. プロジェクト概要

### 背景

話し方を改善したい人が、自分の話し方について客観的なフィードバックを受けるには、話し方スクールや講師によるレッスンを受ける必要がある。

しかし、人による診断には、予約が必要、対応可能な時間が限られる、費用がかかるといった課題がある。

そこで、ユーザーがスマートフォンやパソコンから音声を録音またはアップロードするだけで、AIが話し方を分析し、24時間いつでもフィードバックを受けられるWebアプリを開発する。

初期バージョンでは、一般的な音声データおよび文字起こしデータをもとに、話すスピード、間の取り方、口癖、話の構成などを診断する。

将来的には、アナウンサーや話し方講師の診断基準、フィードバック事例、練習方法などをナレッジとして追加し、専門家の視点を反映した診断へアップデートできる構成とする。

### 目的

ユーザーが音声を録音またはアップロードすることで、自分の話し方の特徴や改善点を簡単に確認できる状態を実現する。

具体的には、以下の状態を目指す。

- 24時間いつでも話し方を診断できる
- 音声を録音するだけで診断結果を確認できる
- 話し方の良い点と改善点を具体的に把握できる
- ユーザーが改善のための練習方法を確認できる
- 過去の診断結果と比較し、成長を確認できる
- 将来的に専門家の診断基準を追加できる
- 話し方スクールの体験診断や集客にも活用できる

## 2. ユーザーストーリー

### 個人利用ユーザー

As a 個人利用ユーザー,
I want ブラウザ上で自分の声を録音できること,
So that 専用の録音アプリを使わずに話し方診断を受けられる.

As a 個人利用ユーザー,
I want 録音済みの音声ファイルをアップロードできること,
So that 過去に録音したスピーチや会話も診断できる.

As a 個人利用ユーザー,
I want 自分の音声をAIに文字起こししてもらえること,
So that 自分が実際に何を話したか確認できる.

As a 個人利用ユーザー,
I want 話すスピードを数値で確認できること,
So that 自分の話す速さが適切か判断できる.

As a 個人利用ユーザー,
I want 話している途中の間や無音時間を確認できること,
So that 間が短すぎる、または長すぎる箇所を把握できる.

As a 個人利用ユーザー,
I want 「えー」「あのー」などの口癖を検出してもらえること,
So that 無意識に使っている言葉を減らせる.

As a 個人利用ユーザー,
I want 話の構成をAIに分析してもらえること,
So that 相手に伝わりやすい話し方へ改善できる.

As a 個人利用ユーザー,
I want 話し方の総合スコアを確認できること,
So that 現在の状態を分かりやすく把握できる.

As a 個人利用ユーザー,
I want 自分の話し方の良かった点を教えてもらえること,
So that 自分の強みを理解し、自信を持てる.

As a 個人利用ユーザー,
I want 改善すべきポイントを具体的に教えてもらえること,
So that 次に何を意識して話せばよいか分かる.

As a 個人利用ユーザー,
I want 自分に合った練習方法を提案してもらえること,
So that 診断後すぐに改善練習を始められる.

As a 個人利用ユーザー,
I want 過去の診断結果を確認できること,
So that 自分の話し方の変化や成長を振り返れる.

As a 個人利用ユーザー,
I want 診断結果を削除できること,
So that 不要な音声データや診断履歴を自分で管理できる.

As a 個人利用ユーザー,
I want スマートフォンから利用できること,
So that 場所を選ばず話し方を練習できる.

### サービス運営者

As a サービス運営者,
I want AIへの診断指示をソースコード内で分離して管理できること,
So that 診断基準を後から変更しやすくなる.

As a サービス運営者,
I want 診断項目ごとの評価基準を管理できること,
So that 将来的にアナウンサーの視点を追加できる.

As a サービス運営者,
I want AIの診断結果を決められたJSON形式で取得できること,
So that 表示のばらつきや解析エラーを減らせる.

As a サービス運営者,
I want 音声解析結果とAI診断結果を分けて保存できること,
So that 将来AIモデルや診断基準を変更して再診断できる.

As a サービス運営者,
I want 診断に利用したプロンプトのバージョンを保存できること,
So that 診断結果がどの基準で生成されたか追跡できる.

## 4. 診断項目

MVPでは、以下の5項目を中心に診断する。

### 4.1 話すスピード

文字起こし結果の文字数と発話時間から、1分あたりの文字数を算出する。

表示項目は以下とする。

- 音声全体の長さ
- 発話時間
- 文字数
- 1分あたりの文字数
- 遅い、適切、速いの判定
- 改善アドバイス

初期の判定基準は一般的な目安として設定し、後から変更できるようにする。

例：

- 250文字未満：ゆっくり
- 250〜350文字：適切
- 350文字超：速い

数値は設定ファイルまたはデータベースで管理し、ソースコードへ直接固定しない。

### 4.2 間の取り方

音声内の無音部分を検出し、回数と長さを分析する。

表示項目は以下とする。

- 無音回数
- 平均無音時間
- 最長無音時間
- 短い間の回数
- 長い間の回数
- 間の傾向
- 改善アドバイス

### 4.3 口癖

文字起こし結果から、以下のようなフィラーを検出する。

- えー
- えっと
- あの
- あのー
- その
- そのー
- まあ
- なんか
- こう
- ちょっと
- やっぱり

検出対象となる言葉は設定ファイルまたはデータベースで追加、変更できるようにする。

表示項目は以下とする。

- 口癖の合計回数
- 口癖の種類
- 口癖ごとの回数
- 100文字あたりの出現回数
- 改善アドバイス

### 4.4 話の構成

文字起こし結果をAIが分析し、話の構成を評価する。

主な評価観点は以下とする。

- 結論が分かるか
- 話題が一貫しているか
- 理由や具体例が含まれているか
- 話の順番が自然か
- 同じ内容を繰り返していないか
- 最後に話がまとまっているか

### 4.5 分かりやすさ

文字起こし結果をAIが分析し、聞き手にとって理解しやすいか評価する。

主な評価観点は以下とする。

- 一文が長すぎないか
- 抽象的な表現が多すぎないか
- 主語や結論が分かるか
- 専門用語が多すぎないか
- 話が脱線していないか
- 情報量が多すぎないか

## 5. スコア設計

総合スコアは100点満点とする。

MVPの初期配点は以下とする。

| 診断項目 | 配点 |
|---|---:|
| 話すスピード | 20点 |
| 間の取り方 | 20点 |
| 口癖 | 20点 |
| 話の構成 | 20点 |
| 分かりやすさ | 20点 |
| 合計 | 100点 |

配点は将来的に変更できるように、設定ファイルまたはデータベースで管理する。

スコアだけでユーザーを否定する印象にならないように、診断結果ではスコアよりも良かった点と改善方法を重視する。

診断コメントは、以下の順番で表示する。

1. 総合評価
2. 良かった点
3. 優先して改善するポイント
4. 具体的な改善方法
5. 次回の練習課題

## 6. AI診断結果のデータ形式

AIの回答は自由記述ではなく、JSON形式で返却させる。

```json
{
  "overallScore": 75,
  "summary": "全体的に聞き取りやすい話し方です。少し話すスピードが速いため、文末で間を取るとさらに伝わりやすくなります。",
  "scores": {
    "speed": 14,
    "pause": 16,
    "filler": 15,
    "structure": 14,
    "clarity": 16
  },
  "strengths": [
    {
      "title": "話題が一貫している",
      "description": "最初から最後まで同じテーマについて話せています。"
    }
  ],
  "improvements": [
    {
      "title": "話すスピードを少し落とす",
      "description": "1分あたりの文字数が多く、文末が聞き取りにくくなっています。",
      "priority": 1
    }
  ],
  "practiceTips": [
    {
      "title": "句読点で止まる練習",
      "description": "読点で0.3秒、句点で0.8秒止まって読み上げてください。"
    }
  ],
  "structureAnalysis": {
    "hasConclusion": true,
    "hasReason": true,
    "hasExample": false,
    "isConsistent": true,
    "comment": "結論と理由はありますが、具体例を入れるとより伝わりやすくなります。"
  }
}
```

JSONの形式はスキーマで検証し、不正な形式の場合は再生成またはエラー処理を行う。

## 7. 非機能要件

### パフォーマンス

- 通常ページの初回表示は3秒以内を目標とする
- 画面遷移は1秒以内を目標とする
- 音声アップロード開始後、進捗状況を表示する
- 1分以内の音声は、原則60秒以内に診断結果を返す
- 診断処理が長引く場合も画面を操作不能にせず、処理中であることを表示する
- 画像やJavaScriptの容量を最小限にする

### セキュリティ

- 認証はSupabase Authを使用する
- MVPではEmailとPasswordによる認証を使用する
- 将来的にGoogle OAuthを追加する
- APIキーはクライアント側へ公開しない
- AI APIの呼び出しはサーバーサイドで実行する
- データベースにはRow Level Securityを設定する
- ユーザーは自分の診断データのみ閲覧できる
- ユーザーは自分の音声データのみ取得、削除できる
- アップロードファイルの拡張子、MIMEタイプ、容量を検証する
- 音声ファイルのURLは原則公開URLにしない
- エラーログに音声内容や文字起こし全文を不用意に保存しない
- 通信はHTTPSを使用する
- 削除された音声と診断データは取得できない状態にする

### プライバシー

- 音声データを診断以外の目的で無断利用しない
- 音声データをAI学習へ利用する場合は、別途ユーザーの同意を取得する
- 音声の保存期間と削除方法を明記する
- ユーザーが音声と診断履歴を削除できるようにする
- プライバシーポリシーに利用する外部AIサービスを明記する
- 初期状態では、診断結果や音声を第三者へ公開しない

### 可用性

- 目標稼働率は99％とする
- Vercel、Supabase、AI APIの障害時は適切なエラーメッセージを表示する
- AI診断に失敗した場合、再実行できるようにする
- 音声保存後にAI診断のみ失敗した場合、再アップロードを不要とする

### スケーラビリティ

- MVPでは同時接続100ユーザーを想定する
- 音声処理と画面表示の処理を分離する
- 将来的に非同期ジョブへ移行できる構成とする
- AIモデルを変更しやすいように、AI API呼び出し処理を共通化する
- 音声認識と文章診断で異なるAIモデルを使用できる構成とする
- 診断項目を追加しても既存機能への影響が少ない設計とする

### ユーザビリティ

- 録音開始、録音停止、診断開始を分かりやすく表示する
- 録音中であることを視覚的に表示する
- 専門用語をできる限り使用しない
- 改善点だけでなく、良かった点も必ず表示する
- 診断結果はスマートフォンで読みやすいレイアウトにする
- スコアの理由を文章で説明する
- 初回利用者でも迷わず診断できる導線とする

### アクセシビリティ

- テキストと背景のコントラストを確保する
- ボタンには分かりやすいラベルを付ける
- キーボード操作に対応する
- エラーを色だけで表現しない
- フォーム項目にはラベルを設定する

### 保守性

- TypeScriptを使用する
- ESLint、Prettierを導入する
- UI、API、データベース処理を分離する
- AIプロンプトを専用ファイルで管理する
- 評価項目と配点を設定ファイルまたはDBで管理する
- 環境変数のサンプルファイルを作成する
- READMEにセットアップ手順を記載する
- 関数やコンポーネントを必要以上に大きくしない

## 18. Claude Codeへの実装方針

Claude Codeで実装する際は、一度にすべての機能を作らず、Phaseごとに実装する。

各Phaseでは、以下の順番で進める。

1. 実装対象の仕様を確認する
2. 必要なファイル構成を提案する
3. データベース変更がある場合はSQLを作成する
4. 機能を実装する
5. 型エラー、Lintエラーを確認する
6. 動作確認方法を提示する
7. 問題がなければ次のPhaseへ進む

既存コードを修正する場合は、現在の構成を確認してから変更する。

以下を守る。

- TypeScriptの型を明確に定義する
- `any`をできる限り使用しない
- APIキーをソースコードへ直接記載しない
- 環境変数を使用する
- クライアント側からAI APIを直接呼ばない
- SupabaseのRLSを有効にする
- コンポーネントを適切に分割する
